## Performance and Identity

The harness creates Markdown cards through the production service and storage
code against an isolated local filesystem and mocked Zotero objects. Each batch
starts from a clean fixture. Per-card latency is measured from progress updates;
the harness RSS is not the RSS of Zotero or Obsidian.

| Input | Success / failed / pending | Total elapsed | Per-card p50 / p95 | Harness peak RSS | Queue   |
| ----: | -------------------------: | ------------: | -----------------: | ---------------: | ------- |
|     1 |                  1 / 0 / 0 |      51.59 ms |   51.59 / 51.59 ms |        190.2 MiB | drained |
|   100 |                100 / 0 / 0 |     167.60 ms |     0.91 / 2.66 ms |        190.5 MiB | drained |
|  1000 |               1000 / 0 / 0 |   1,211.17 ms |     0.77 / 2.45 ms |        205.8 MiB | drained |

For comparison, the pre-optimization 1000-item run took 127,099.54 ms. The
main cost was a full recursive Markdown identity scan for every new source.
Batch processing now builds the source identity inventory once, updates it as
cards are written, and checkpoints the card index every 25 changes. A one-shot
checkpoint write failure is retried once; batch completion still flushes the
remaining index state. The latest run reconciled all 1000 inputs to 1000 unique
source IDs and 1000 unique card IDs. These are local fixture timings, not a
production-host or UI responsiveness guarantee. Repeated 1000-item fixture
runs ranged from 812.81 to 1,224.51 ms on this machine.

The R6 fixture also preserved a 280,000-byte annotation body and a 2,097,152-
byte image resource byte-for-byte, verified the content hash and Markdown
reference, and removed the incomplete temporary resource after an injected
commit failure. Image decoding was mocked in this service-level stress
fixture; decoder behavior is covered separately by the image-resource tests.

## Failure Boundaries

| Case                                      | Result                      | Evidence                                                                                                                                                                                                                                 |
| ----------------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Card content write fails before commit    | PASS                        | No partial note remained; retry created one card.                                                                                                                                                                                        |
| Injected `EACCES` write denial            | PASS (injected)             | No card was created by the denied write; retry succeeded.                                                                                                                                                                                |
| Actual read-only output directory         | PASS                        | Temporarily removed write bits from the disposable fixture directory; the production card writer failed with `EACCES`/`EPERM`, left no note, then succeeded after permissions were restored. | Card file commits but index write fails   | PASS                        | Retry discovered the existing `bridge_source_id`, reused its `bridge_card_id`, and did not create a second file.                                                                                                                         |

## iCloud Drive Observation

A unique disposable directory, `Bridge R6 Test 2026-10-28`, was created in
iCloud Drive. The Markdown file under `Zotero Literature/Special 中文 C++/`
contained 89 bytes and SHA-256
`dbe3a503e2c018bbf188090ab2d63f132ec0792d878ee6d434bded749f4568a5`.
`fileproviderctl evaluate` first reported `isUploaded=1` and `isDownloaded=1`.
Finder's **Remove Download** action then produced `isUploaded=1` and
`isDownloaded=0`. Reading the file triggered hydration; its bytes and hash
matched, and File Provider returned to `isDownloaded=1`.

This verifies ordinary upload, eviction to a placeholder, and hydration on the
same Mac. It does **not** verify a real cross-device conflict copy or an actual
network/File Provider outage. No second device/account was available. The
dedicated test directory was moved to Finder Trash after the checks; the
primary Obsidian Vault was not used.

## Live Long-Run Observation

The 30-minute test ran in the already-open isolated `test-vault` from
2026-10-28 08:19:08 UTC to at least 08:49:19 UTC. The disposable note was
edited through the Obsidian UI at timed intervals, with periodic note switching
and edit/reading-view transitions. All 36 sequential edit markers and the
initial personal-note text remained present. Companion status stayed
`connected`. The final on-disk note SHA-256 was
`37da446b076098d36b0e530bd0bb78ceba7b958262d9e27471f905560f8a6f8a`.
Obsidian RSS samples ranged from about 121 to 131 MiB; Zotero samples ranged
from about 116 to 184 MiB. These sparse snapshots show no monotonic growth, but
are not a formal heap/profile analysis.

The companion was disabled and re-enabled from the test Vault's Community
Plugins settings. Its toggle returned to enabled and the open test note again
reported `Zotero Bridge: connected`. The same card was also opened in two tabs
and remained readable with its content intact. The primary Obsidian process is
shared with the user's other open Vaults, so it was not restarted during R6;
R3 already covered application restart behavior in its isolated lifecycle
matrix. Zotero remains the verified project-isolated instance.
