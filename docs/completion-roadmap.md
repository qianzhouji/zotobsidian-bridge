## 1. 交付目标与现状

最终交付目标：在 macOS 上，从 Zotero 阅读、批注、记录 Markdown 笔记，到 Obsidian 文献卡片的持续更新，形成可安装、可恢复、可验证的工作流。

完整功能范围包含：已保存 PDF 文字批注、历史批量导入、Zotero 内 Markdown 编辑、来源更新、冲突恢复、原生 Zotero 笔记导入、图片批注、用户明确选择范围后的自动建卡，以及可选的 Obsidian companion。R4-A、R4-B 已通过各自隔离现场矩阵。R4-C 范围内/外收录、历史批次跨重启恢复及现场中途取消/续跑均已通过；不可用文库安全拒绝通过隔离实测，读取拒绝错误呈现和“无批次创建”由运行时故障注入覆盖。Zotero 标准群组设置不能形成成员可见但不可读的 ACL，因此该状态不适用；具名私有群组的非成员可见性仍待由另一账号持有的测试组和独立非成员登录完成。R5 隔离 UX 矩阵已通过；单独的全新 profile 冷启动入门演练尚未执行，见 [`r5-execution-report.md`](r5-execution-report.md)。

约束：先交付单机桌面版本；多设备并发同步、手机端、OCR 和自动生成知识双链不属于本轮交付。iCloud 测试验证单机使用云盘时的文件行为，不代表实现分布式同步。插件创建的来源链接用于回到文献；不自动安排概念笔记之间的链接。

当前已有：Zotero 插件主体、卡片身份和来源字段管理、编辑器、同步队列、批量操作、companion、原生 Zotero 笔记导入、图片资源、R4-C 范围自动建卡与可取消/恢复历史批次、R5 配置/恢复/诊断体验、构建和本地测试脚本。当前缺少：具名私有群组的非成员可见性实测、单独的 R5 全新 profile 冷启动入门演练、R6 双设备冲突/实际不可用恢复/全量桌面验收、R7 远程 CI 与干净安装升级/正式发布身份，以及 R8 候选版试用。R6 已有阶段性本地压力与单机 iCloud 文件提供者证据，详见 [`r6-execution-report.md`](r6-execution-report.md)。R7 的自动化矩阵和 release preflight 已在本地实现，当前 Git remote 仍指向 Zotero 插件模板，因此远程验收和正式 ID 必须等项目仓库明确后执行，见 [`r7-execution-report.md`](r7-execution-report.md)。若未来需要验证另一种服务端 ACL 中的真实读取拒绝，应另建对应的测试服务/账号夹具。

先前的完成百分比是粗略判断，不是测试覆盖率。后续采用逐项验收；“代码存在”“本地自动测试通过”“桌面实测通过”“可发布”分别记录。

## 3. R0：固定开发基线

### 开发目标

让后续每次修复、测试和打包都能对应一个确定的代码版本，并保护已有开发成果。

### 工具与执行

1. 用 Git 检查当前修改、未跟踪文件和上游模板来源，梳理哪些是项目源码，哪些是生成物。先检查敏感信息，再建立本地基线提交；不将 `.env`、真实文库、测试数据库和依赖目录纳入版本管理。
2. 保留 Node 版本文件、两个 lockfile、Zotero/Obsidian 版本及 macOS、芯片、内存信息。现有文档记录的 Zotero 10.0.6、Obsidian 1.14.4 是开发基线，执行时重新核对安装版本。
3. 整理需求清单、缺陷清单、验收用例和版本迁移规则；给每项分配固定编号。
4. 建立独立 Zotero profile、数据目录、本地测试 Vault、本地队列和测试 PDF 集；iCloud 用单独的测试目录。真实学习 Vault 不作为测试夹具。

### 验收标准

- 从基线的干净检出执行两个 `npm ci` 后，现有构建和本地测试可复现。
- 每个后续任务能对应需求编号、相关模块、测试用例和状态。
- 启动和停止测试 Zotero 不影响正常 Zotero 实例；测试记录可证明路径隔离。
- 私有数据和本机配置未进入源码提交或安装包。

交付物：基线提交、环境记录、需求/缺陷清单、测试数据目录说明。

## 4. R1：修复写入一致性和请求生命周期

### 已观察到的优先问题

下面来自当前代码阅读，是需要修复或用回归测试确定边界的事项；不代表已经在真实文库触发过数据损失。

| 编号  | 当前实现与问题                                                                                                                             | 修复方向                                                                            |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| R1-01 | `submitCompanionWrite` 等待约 1.5 秒后退出；当前函数内没有超时后的持续回执消费流程                                                         | 持久保存操作和请求的对应关系，启动和后台恢复迟到回执，更新业务任务、索引和确认状态  |
| R1-02 | `card-updater.ts` 先读取原文并生成新内容，`vault-storage.ts` 随后重新读取文件生成 baseRevision；两次读取之间的外部编辑可能成为错误的新基线 | 将生成内容时的原始版本传到写入层，不能给旧内容配上后来读取的版本号                  |
| R1-03 | 请求有输出目录，却没有明确的目标 Vault 配对身份                                                                                            | 加入持久的配对 ID、Vault ID 和协议握手，拒绝错误 Vault 或不兼容版本                 |
| R1-04 | companion 的处理标志在异步创建队列目录后才设置                                                                                             | 在首次 await 前取得处理权，确保轮询、手动命令和设置回调不能重叠启动处理             |
| R1-05 | companion 将大部分处理异常统一写成 conflict                                                                                                | 区分编辑冲突、暂时 I/O 错误、不可用资源和非法协议；为可重试错误提供有界退避         |
| R1-06 | 写入模式切换主要检查在途写入和未回答请求；设置与崩溃后的配对状态仍需统一                                                                   | 将 Vault、队列、输出目录、写入模式作为整体配置迁移；持久记录切换状态并确定恢复规则  |
| R1-07 | companion 的路径检查主要基于字符串规范化和目录前缀                                                                                         | 对目标目录和队列的真实路径、符号链接、大小写规则补检查，并测试跨 Vault 路径拒绝行为 |

### 工具与开发路径

使用 TypeScript、Node 测试工具、临时文件系统夹具和可控延迟/故障注入。主要修改 `src/adapters/companion-*`、`src/adapters/vault-storage.ts`、`src/services/card-updater.ts`、`src/services/preferences.ts`、`src/core/writer-transition.ts` 和 `obsidian-plugin/src/main.ts`。

1. 先为 R1-01 和 R1-02 编写能够复现错误或缺失行为的测试，再修改实现。
2. 为逻辑操作保存稳定 operationId；发送前保存 requestId，重试和重启继续追踪同一操作。只有确认提交结果后才能将业务任务标为完成。
3. 定义持久状态：待发送、已发送、等待回执、已应用、冲突、待重试、已确认。错误信息必须能定位到卡片和操作，重试不得无界生成重复请求。
4. 卡片创建成功但回执丢失时，按稳定身份和操作记录恢复索引，禁止把已创建的卡片当成另一张新卡。
5. 传递原文哈希并在 Obsidian `Vault.process()` 中校验。对于来源字段更新，只修改插件拥有的区域；不同字段发生并行修改时，先重新读取、合并，再创建新的操作版本。
6. 直写模式的原子替换只能防止文件写到一半，不能自动解决外部进程并行编辑。为其补基线检查和明确限制；需要并行编辑保障的流程由 companion 负责，不能把“原子写”宣传为跨应用事务。
7. 在回执和 ACK 清理的每个中断点验证重启行为；保留有限、可查询的完成记录，避免孤立回执永久阻塞设置修改。
8. 配对切换先停止新操作入队，等待已接收操作结算，再切换。超时、取消和进程退出都有明确恢复路径，不能恢复后猜测启用另一个写入者。

### 验收标准

- Obsidian 关闭、请求超时、稍后启动 Obsidian：原请求最终成功，Zotero 接收迟到回执并修复任务/索引；队列能收敛。
- 请求重复提交十次，只产生一个逻辑结果；创建、更新、确认前后重启均不复制卡片或回退正文。
- 在“读原文”“生成新内容”“提交写请求”“真正写入”之间分别注入外部编辑：用户修改保留，旧操作冲突或安全合并。
- 配对到错误 Vault、非法目录、越界路径或符号链接出口时，目标和外部文件都不改变。
- 手动处理、轮询和设置保存同时触发，最多只有一个消费者处理当前队列；退出插件后不再继续接收新任务。
- 临时写失败可恢复；永久协议错误明确报告；不能因一条损坏请求永久阻塞所有其他卡片。
- 同一卡片的连续更新按明确版本顺序结算；较旧的延迟请求不会覆盖较新内容。
- Vault/队列/模式切换遇到待处理操作时被阻止或有序等待；崩溃恢复后仍满足单一写入者约束。

交付物：修复代码、独立的协议/生命周期回归套件、更新后的协议文档和故障矩阵。

## 5. R2：真实 Zotero 基础工作流

### 工具与开发路径

使用独立 Zotero profile、真实测试 PDF、Zotero 调试日志和开发者工具。优先使用类型定义及对应版本的官方接口；对未公开或不稳定的界面入口做兼容探测。

1. 安装构建的 XPI，逐一检查选区入口、批注侧栏入口和批注菜单，验证传来的 ID 确实对应保存的批注。
2. 明确未保存选区的行为：提示先保存批注，或实现经验证的保存流程；不得悄悄关联到别的批注。
3. 用有父文献的 PDF、独立 PDF、同一文献多个 PDF、中文标题、不同页码标签测试建卡与跳转。
4. 检查文献信息映射、文件命名、Paper.md、Annotations 目录和多次操作的复用行为。
5. 在真实窗口里验证 CodeMirror、KaTeX、中文输入、自动保存和冲突选择。当前独立编辑窗口先作为交付入口；若原生小批注浮窗不能稳定扩展，保留明确可用的入口并记录限制。

### 验收标准

- 每个宣称支持的入口完成至少一次建卡、重复打开、编辑保存和来源更新；UUID 与文献/PDF 身份一致。
- Zotero→Obsidian 打开正确卡片；卡片→Zotero 返回正确 PDF 页。页面标签与内部页号不同时仍可追溯。
- 中文输入法组合过程中不会抢走焦点、截断文字或提前保存半个输入。
- 公式、代码块、列表、表格、撤销/重做和手动保存正常；来源区域不可误编辑。
- 暂时断开 Vault 后仍保留草稿，恢复路径后可完成保存；错误状态可见。
- 文献元数据变化只更新受管理字段；用户正文和自定义 YAML 保留。

交付物：带应用版本、输入夹具和截图/日志的桌面验收记录，以及对应修复。

## 6. R3：真实 Zotero–Obsidian 联调

### 工具与开发路径

使用独立 Obsidian 测试 Vault、companion ZIP、Obsidian 开发者工具、R1 的请求日志和 Zotero 测试实例。

1. 安装 companion，完成 Vault 身份与本地队列配对，并呈现连接、等待和冲突状态。
2. 在两端关闭、重启、同时编辑、延迟保存的情况下验证协议；每次检查界面中的内容和磁盘文件。
3. 对同一文件在阅读视图、源码视图、实时预览以及多个窗口/标签中打开的状态分别测试。现阶段“打开即延迟”的策略需要可理解的等待提示和关闭后恢复行为。
4. 验证移动/重命名卡片、重复身份、多个 Vault、插件禁用/启用以及模式切换。

执行状态：companion 已补充队列单写入者锁、可读状态和复制 Vault ID 命令；隔离自动化覆盖关键队列恢复与冲突场景。R3 的 Reading/Source/Live Preview、多标签、多窗口、双端带在途请求重启、迟到 ACK、真实 writer-mode 转换与保护、移动卡片后的来源更新、错误 Vault ID 拒写及双 Vault 单消费者验收均已在隔离桌面环境完成；移动卡片更新保留用户正文与 YAML，companion 请求/响应/ACK 队列最终清空。写入后响应丢失通过自动化故障注入验证，尚未在桌面上于精确指令边界强杀进程。详见 [`r3-execution-report.md`](r3-execution-report.md)。

### 验收标准

| 场景                               | 必须观察到的结果                                     |
| ---------------------------------- | ---------------------------------------------------- |
| Zotero 提交时 Obsidian 未启动      | 可见等待状态，启动后完成，原操作得到确认，无直写回退 |
| Obsidian 正在编辑同一张卡片        | 输入不消失、不跳回旧版；请求延迟或明确冲突           |
| 先保存 Obsidian 修改，再处理旧请求 | 旧请求不得覆盖修改；冲突有可操作的解决入口           |
| 已写文件但尚未写回执时中断         | 重启后识别已应用结果，不重复建卡                     |
| Zotero 已超时后收到回执            | 状态、索引和确认记录最终一致，不遗留无法处理的任务   |
| 移动卡片、切换 Vault               | 按身份定位或明确提示；不能写入旧目录、错误 Vault     |
| 队列非空时切换模式/路径            | 不出现两个写入者；失败后配置仍可恢复                 |
| 并行打开两个配对实例               | 第二个实例被拒绝或取得受控所有权，不无锁并行消费     |

交付物：双应用故障矩阵全项结果、配对操作说明、已知兼容限制。

## 7. R4：补齐内容扩展

本阶段拆成三个独立交付项。每项都要复用 R1 的身份、字段所有权和写入协议，并分别测试直写与 companion 的适用行为。

### R4-A：Zotero 原生笔记

工具：Zotero 当前版本笔记接口、HTML DOM 解析器、经过选型的 HTML→Markdown 转换库、固定输入/输出测试夹具。先确认 Zotero 笔记实际格式，不将 HTML 原样当作 Markdown，也不用正则表达式承担 HTML 解析。

## 9. R6：可靠性与环境验收

### 工具与开发路径

使用 Node 夹具、实际 Zotero/Obsidian、macOS Activity Monitor 或应用 profiler、文件哈希、独立 iCloud 测试目录。对真实宿主采用其调试工具；Playwright 仅适合独立可浏览器运行的组件测试，不能代替 Zotero/Obsidian 宿主验收。

1. 测试 1、100、1000 条批注，以及包含较大笔记和图片的批次。记录运行时间、每条操作 p50/p95、UI 响应、内存、队列长度与资源数量。
2. 持续编辑至少 30 分钟，并执行重复的打开/关闭、插件启停和两端重启；检查监听器、计时器和内存是否持续累积。
3. 在写入、确认、索引保存、资源提交等边界中断进程；测试只读目录、权限不足、暂时不可用和可模拟的磁盘写失败。
4. 在测试 iCloud 目录验证未下载占位文件、临时不可用、文件延迟和冲突副本。不能把暂时不可读取误判为用户永久删除。
5. 复测中文路径、空格、特殊字符、页码标签、重复身份、群组权限和多个 PDF 附件。

### 验收标准

- 1000 条测试中卡片与稳定来源身份一一对应；成功、失败、待处理的数量之和与输入一致。
- 批量取消在当前受控操作完成后停止，不再启动下一条；单次操作有超时/等待状态，取消不能永久无响应。
- 所有数据保护用例零静默覆盖、零错误文献关联；故障后每项结果可解释且可恢复。
- 30 分钟编辑和重复启停没有累积的重复监听或重复任务；内存/耗时记录可复核，若有持续增长须定位修复。
- 首轮测量建立具体机器基线；后续同配置关键耗时或稳定内存退化超过 20% 时调查原因。该阈值是工程告警线，不是已达到的性能承诺。
- 云盘异常不会导致空文件覆盖或自动重建重复卡片；冲突副本可识别或明确提示人工处理。

交付物：性能基线、长时间测试记录、故障报告、明确的支持环境列表。
